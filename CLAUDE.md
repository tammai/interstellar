## Working on this

```sh
make dev      # run at :8422 against ./.devdata, UI served from disk
make test     # offline suite; never touches a network or a provider
make test-ui  # the star map's pure layout logic (node)
make lint     # vet + gofmt
```

Three conventions worth knowing before you write code here:

- **Tests never make live calls.** `make test` must stay runnable with a provider key exported in the shell and cost nothing. Test helpers clear provider env vars explicitly; a test that resolved a real provider once did bill a real account. The single exception is `cmd/verify-classifier`, which is opt-in and says so.
- **`go:embed` bakes the UI into the binary.** `make dev` sets `INTERSTELLAR_WEB_DIR` to serve `web/assets` from disk instead. Without it, a CSS or JS edit does nothing until you rebuild, and the resulting "my change had no effect" is a genuinely confusing hour.
- **Assets served from disk are sent `no-store`; embedded ones stay cacheable.** This is the previous convention's sibling and the worse half. `http.FileServerFS` sends `Last-Modified` and no `Cache-Control`, which is enough for a browser to cache heuristically — so in development an edit that IS on disk and IS being served still does not reach the page. It presents as the same "my change had no effect", but survives every check you would run to diagnose it: the file is right, the server's response is right, and a fresh browser renders it correctly. `withNoStore` is the single place cache policy is decided, and `main` tells it which case is in play via `Server.WebFromDisk` — only `main` knows. Embedded assets stay cacheable on purpose: they cannot change without the binary changing, which is a new container. A test pins both directions.

## What this is

A per-user AI news intelligence tool. One Docker container per person, `docker run -p 8422:8422 -v interstellar-data:/data`. A scheduler ingests feeds each morning, an LLM classifies items against the owner's topics, a second LLM pass clusters matched items into **signals** (cross-source stories), and a canvas star map renders today's signals as a sky. The yardstick is habit: "do we each actually open it every day?"

## Architecture

Single Go binary, no sidecars. Everything ships inside it:

```
scheduler (in-process cron, honors TZ)
  09:30 ingest ──▶ SQLite /data/interstellar.db
  10:30 classify + compose signals
HTTP server :8422
  /        embedded UI (go:embed)
  /api/*   sky data, signal detail, settings, POST /api/refresh
LLM client ──▶ provider registry ──▶ OpenAI-compatible /chat/completions
```

Locked stack choices (spec §3, with reasons — don't relitigate):

- **Go, single binary, `go:embed` for UI and fonts.** Rejected: Node/TS (heavier image), Python (packaging friction).
- **Pure-Go SQLite driver, `CGO_ENABLED=0`.** The whole point is trivial multi-arch (amd64 + arm64). A cgo driver breaks that.
- **SQLite, one file in `/data`.** Single user, single writer; backup is `cp`. Not Postgres.
- **Embedded LLM client with a provider registry, not a proxy.** See below — this is the part most likely to be misremembered.
- **Web UI is the front door.** No email, no notifications, no auth in Phase 0.

### The LLM layer is a registry, and one transport

§3.1 is a hard requirement, not a preference: *either role can run on any model from any provider, switched via settings without touching code or restarting.*

- **Providers** are named registry entries `{base_url, api_key_env}` stored as JSON in `settings`. Presets ship for deepseek, anthropic, google, openrouter, litellm, and ollama (keyless), plus anything the owner adds. An entry with an empty `api_key_env` sends no `Authorization` header.
- **Keys are referenced by env var name, never stored.** The registry holds the *name*; the value is read from the environment at call time. No endpoint ever returns a key value — `/api/settings` returns the name plus a resolved/unresolved boolean.
- **Roles are `provider/model` refs, and only the FIRST slash separates.** `classifier = openrouter/deepseek/deepseek-chat` is provider `openrouter`, model `deepseek/deepseek-chat` — OpenRouter's own model ids contain a slash, so the ref nests rather than breaking. `synthesizer = anthropic/<sonnet>` is the unnested shape. Roles mix providers freely.
- **Fallback chains are cross-provider.** A retry can land on an entirely different vendor, so base URL and auth are rebuilt per hop, and every attempt gets its own `llm_calls` row — a fallback that fires must be visible in the cost log, not silent.
- **One transport, forever.** OpenAI-compatible chat completions is the only wire format. §3.1 puts native Bedrock/Vertex/Foundry auth explicitly out of scope: *"never native cloud SDKs in-app."* If corporate billing ever matters, that's a registry entry pointing at a LiteLLM gateway. Do not add a vendor SDK dependency to solve a provider problem — the registry is the extension point.
- **No restart, ever.** Effective config is resolved per run, not cached at boot. Nothing may hold a settings snapshot across runs, and a settings change touching the schedule rebuilds the cron entries in place.

Phase 0 seeds all three roles to `openrouter/deepseek/deepseek-chat` — the cheap-first posture decided 2026-08-11 (~$3/month/instance), routed through OpenRouter since spec **rev 6, decision #23** (2026-09-05). Same model, same cost order; only the route changed, and the route is the point. Every rung of §3.1's escalation ladder is a *different vendor*, so against DeepSeek's own endpoint climbing it meant adding an environment variable — which §7 fixes at boot, i.e. a restart, which §3.1 forbids. One OpenRouter key reaches every rung, so the ladder becomes what the spec says it is: a settings change. Two accepted costs: OpenRouter bills a margin over the vendor's own price, and the data path now runs through OpenRouter *and* whichever vendor it routes to, so §3.1's note on where topic definitions travel applies to two parties. The `deepseek` preset still ships — pointing a role back at `deepseek/deepseek-chat` restores rev 3's direct routing exactly. When quality forces a change, the ladder is the runbook — classifier fails the JSON gate → google flash tier → anthropic haiku; digest reads poorly → anthropic sonnet. Each step is a settings change, not a code change.

### The unit of the product is a *signal*, not an item

An `item` is one URL from one feed. A `signal` is one cross-source story for one topic, composed by the synthesizer LLM, and it is what the sky renders — one star per signal. `source_count` drives the gold "hot" flag (≥3) and the glow; `score` drives size; age drives opacity. When you touch the pipeline or the API, think in signals.

Deduplication happens at two levels and they are not the same mechanism: URL canonicalization + `INSERT OR IGNORE` at ingest time (exact same link from two feeds), and LLM clustering at synthesis time (different links telling the same story). Spec §4 calls this out explicitly.

### Pipeline stages

`ingest → classify → compose signals`, each idempotent and separately restartable. Per-source try/continue: a dead feed must never abort the run (`last_run_at` updates on success only). Classification is **per topic**, batched ~30 items — deliberately not one 7-topic mega-prompt, because per-topic calls give sharper verdicts and free per-topic hit-rate stats.

## Non-negotiable behaviors

These come straight from spec §10 (acceptance criteria) and §6 (UI contract). Breaking one is a bug even if tests pass:

- A dead feed does not break ingest; re-ingesting creates zero duplicates.
- Reassigning a role to a different provider in Settings takes effect on the **next run, with no restart**, and the per-role "test call" button verifies it in-UI.
- Classifier JSON parses 100% on a 200-item sample. This gates any model swap. Assume the model returns fenced or prose-wrapped JSON sometimes and extract tolerantly.
- The LLM call cap aborts a runaway run and surfaces a banner in the UI — the cap is the replacement for LiteLLM's budget guard, so it must actually stop the run, not just log.
- Kill the container mid-run, restart, next run is clean and the DB is intact.
- `prefers-reduced-motion` disables twinkle, pulse, glint, and parallax easing. Keyboard focus stays visible. Layout works to ~380px.
- Empty topics render "No signal today" rather than disappearing.
- Fonts are **bundled** (Noto Sans, Playfair Display — both OFL). No hotlinking; the UI renders offline. The prototype's Google Fonts `<link>` must not survive into the real UI.
- No 3D rotation of the star map. Rejected with cause: there is no third data dimension and it breaks spatial memory.

## Conventions

- Provider API keys come from env only, referenced by the name the registry stores (`OPENROUTER_API_KEY` for the seeded default, `ANTHROPIC_API_KEY`, …). Never write a key value to the DB, never return one from an endpoint, never log one.
- Config lives in the `settings` table and is resolved per run. `PORT` and `TZ` are the only process-level env knobs besides the provider keys.
- Every LLM call attempt gets a row in `llm_calls` (run date, role, **provider**, model, token counts). Cost visibility is a feature, and it feeds the Phase 3 habit analysis.
- **`llm_calls` records the reply's quality next to the call's cost, and the two answer different questions.** `ok` is transport; `items_in`/`items_out`/`parse_ok`/`repair` (migration 008) are whether the answer was any good. The gap between them shipped as a week of near-empty skies: a prompt asking for a top-level array under `response_format {"type":"json_object"}` comes back as **one** object on several providers, so a 12-item batch returned a single verdict — 200, valid JSON, plausible tokens, nothing failing anywhere. The only symptom was topics matching almost nothing, which is indistinguishable from a definition drawn too tight, and the seeded `deepseek-chat` tolerated the array shape so it only appeared once the roles moved. `store.ModelReliabilityOver` groups the log by provider/model/role into a parse rate and a **completeness** rate (`GET /api/models/stats`, rendered under the hit rate on Settings → Signal quality), which is what turns §3.1's escalation ladder from a runbook into a measurement — a model that is cheap and answers 4 of 30 items is not cheap. Four rules hold it together. **`Request.Expect`/`Repair` describe the question**, so the client writes them on every attempt including failures; **quality is attached afterwards by row id** (`Client.ReportReply`), because the row has to exist before the reply is parsed and because classify runs batches concurrently — `last_insert_rowid()` would cross-attribute one worker's reply to another's call even with the pool capped at one connection. **`items_out` counts answers to THIS batch, once each** — `keepAnswers` whitelists ids against the batch and deduplicates before `ReportReply` sees them, so completeness can never exceed 1.0. It could, and did (3427 answered against 3423 asked, observed 2026-09-08): the whitelist rejected hallucinated ids but let a REPEATED id through twice. `matches` has `PRIMARY KEY (item_id, topic_id)` and is upserted, so this was never data loss — it was measurement loss, in the two places measurement is load-bearing. An over-answering batch cancels out one that silently truncated inside the same provider/model/role group, which is precisely the failure completeness exists to catch; and the duplicate inflated `MatchesKept`, i.e. the numerator of the hit rate used to judge whether a topic definition is too tight. First verdict for an id wins, because taking the later one makes a stored score depend on reply ordering. **Completeness sums only rows that were assessed** (`parse_ok IS NOT NULL`): an attempt that died in transport asked for 30 items and got no reply, and counting its `items_in` charges the model for a 500. And **zero `items_in` is stored as NULL, never 0** — a chat answer, a transcript summary and a test call are not lists of anything, and a zero there would join the denominator of every rate they share a group with. Report on every reply you *tried* to parse, failures included: a parse failure recorded is §10's JSON gate per model, and a parse failure not recorded is indistinguishable from a call that was never asked for records. Two deliberate omissions — the synthesizer's completeness counts **items covered, not stories** (grouping thirty items into eight stories is the job being done well), and the weekly round-up reports nothing, because one call a week is no sample and its `items` list is a *choice* of twelve from sixty rather than a coverage requirement.
- Schema changes go through the embedded migration path, never hand-edited SQL against a live DB. Migrations are append-only: never edit one that has shipped, add the next number.
- **A new table referencing `items(id)` or `sources(id)` must be cleaned up in `store.DeleteSource`.** No foreign key here declares `ON DELETE CASCADE` and the pool runs with `foreign_keys(on)`, so a missed clause is not a stale row — the delete fails, the transaction rolls back, and the source stays on the list. `item_transcripts` shipped this way: only video items carry a transcript row, so every other kind deleted cleanly and a YouTube channel could not be deleted at all. Delete the dependent rows for orphaned items only, in the same transaction, before the items themselves; an item another source still carries keeps its row, because that row is a permanent answer (a video with captions disabled) and dropping it makes the next run refetch forever.
- **The connection pool is capped at one.** Never issue a query while a `*sql.Rows` is still open — the open rows hold the only connection, so the inner call waits on a connection the outer loop won't release. It hangs rather than erroring. Drain into a slice, close, then do the follow-up work; `store.SignalByID` is the worked example.
- **Per-topic stats and the classify watermark commit together, in one transaction** (`store.CommitClassifyPass`). They are not independent writes. Stats written without the watermark count the same items again on the next pass, inflating every denominator and understating every hit rate; the watermark without the stats loses a pass that can never be recomputed, because `matches` keeps score ≥ 4 verdicts only and the denominator exists nowhere else. For the same reason an **aborted** pass — cap breached, context cancelled — records neither, including for the batches that did succeed. `ItemsConsidered` counts only batches the model answered: a failed batch is not a denominator, or a provider's bad afternoon reads as a badly defined topic.
- **Search is FTS5 inside the pure-Go driver, and user input never reaches `MATCH`.** `modernc.org/sqlite` ships FTS5 with `bm25()` and `snippet()`, so full-text cost no new dependency and `CGO_ENABLED=0` is intact. `store.BuildMatch` is the only way prose becomes a query: it quotes every token and OR-joins them, because FTS5 treats `AND OR NOT NEAR " * : ^ - ( )` as operators and an ordinary question like `what's happening with agents?` is otherwise a syntax error — or worse, silently parses as something else. It returns `""` for unsearchable input, which callers must treat as **filter-only, never match-everything**. The indexes are `content=`-external, so **the triggers in migration 003 are load-bearing**: `ReplaceSignals` deletes and re-inserts on every compose, so a missing delete trigger means yesterday's removed stars keep coming back as hits.
- **The chat planner emits a typed `AskQuery`, never SQL,** and `Asker.sanitizePlan` is the whitelist every field passes through. A hallucinated topic id is the dangerous case: left in place it filters everything out and produces a confident "nothing happened", so unknown ids are dropped rather than trusted. Text-to-SQL is rejected here on *correctness* grounds before security ones — wrong SQL returns a plausible answer to a different question, with nothing to notice it by.
- **All three roles are on the Model screen, chat included.** It was not, for a while: `chat_model` had a settings key, a `RoleChat` chain and its own branch in `/api/model/test`, but no section in the UI — so the only way to move Ask off the seeded `deepseek/deepseek-chat` was to PUT JSON at the API by hand, which stranded an owner whose credit at that provider ran out. §3.1's "switched via settings without touching code" is not satisfied by a role the settings screen does not draw. Its section carries `max_chat_calls_per_day` too, because that budget belongs with the role it governs and not with Schedule's run caps, and its save confirmation says "your next question" rather than "the next run" — chat is not a run.
- **Readiness says whether the config COULD work; `store.FailingRoles` says whether it DID.** They are different questions and the gap between them shipped as a silent outage: a keyless provider (Ollama) whose subscription lapsed answers 403 to everything, `RoleReadiness` reports it ready because there is no key to be missing, and the only symptom is a sky saying "nothing yet today" — 63 failed classifier calls in one run, invisible. `FailingRoles` reads what happened: for each role's most recent day with any calls, **every call failed and none succeeded**. Not "any call failed" — a fallback chain doing its job is failures followed by a success, which is already in the cost log and would cry wolf on every transient 500. The `test` role is excluded (its result is shown inline the moment the button is pressed). The banner ranks this **above** the daily cap, because a dead provider burns the budget on retries and raising the cap just buys more 403s. Chat failures travel in `status.failures` but stay off the star map's banner — a dead Ask screen must not dress itself up as a broken morning run, same reason it is out of `Ready()`.
- **Provider error bodies are unwrapped to the sentence, not stored as the envelope.** `llm.snippet` prefers `{"error":{"message":…}}`'s message, which is the only part naming what to do; the envelope around it is long enough to push that message out of a truncated banner entirely. It falls back to the raw body for anything else — a wrong `base_url` returns an HTML page with no envelope, and its first line is the clue — and deliberately does not guess at valid JSON of an unknown shape.
- **Chat is budgeted separately and is not part of `Ready()`.** `RoleChat` has its own `max_chat_calls_per_day` and is exempt from the per-run cap, because a question is not a run. Critically, `Config.Readiness()` still covers only classifier and synthesizer: `run.go` refuses to start when `Ready()` is false, so folding chat in would mean an owner who cleared `chat_model` silently broke their morning ingest. Use `RoleReadiness(RoleChat)` for the chat screen instead. A test pins this.
- **The secondary screens load none of the star map.** `web/assets/chat/` and `web/assets/settings/` are separate documents sharing only `tokens.css`. Neither creates a canvas and neither ever calls `requestAnimationFrame` — verified in-browser, not assumed (measured: settings loads exactly `tokens.css`, `settings.css`, `settings.js` and calls rAF **0** times; the sky calls it ~60/s). Keep it that way: the reason they exist is that `sky.js` is 56KB and a frame loop, and neither answering a question nor editing a topic definition needs either. Palette and `@font-face` live in `tokens.css` precisely so three screens cannot drift into three palettes. The palette's three text tiers are a **measured ladder** against `--space-2`, the lightest surface they sit on: ink 11.6, ink-dim 7.0, ink-faint 4.6 — all clearing WCAG AA. `--ink-faint` was 2.41 and carried ~38 roles including every settings field label, so it was not decoration failing quietly but the body copy of the configuration UI; raising it alone would have collapsed it into ink-dim, which is why both moved. Keep a new tier inside the ladder rather than inventing a fourth, re-measure before darkening any of the three, and do not fade text with opacity to signal state — fade an `<img>`, which has no contrast requirement.
- **Ask is entered from a dock at the bottom centre of the sky, and it is still a plain link.** It replaced an icon button in a row of icon buttons, which said only "there is a feature"; the dock is the shape and the place every chat application puts its input, so it says "type a question here" without a label. It carries **no handler and no input** — typing there would mean the star map loading the chat screen's code, and chat being a separate document that loads none of `sky.js` is the entire point of it. The `#ask` fragment is what focuses the composer on arrival, and `chat.js` focuses **only** on that fragment: a bookmark, a reload, or Back from an article must not throw a keyboard over the transcript. It sits after `#panel` in the DOM purely so `#panel.open ~ .ask-dock` can move it out of an open detail panel's way in CSS, with nothing in `app.js` knowing either element exists — and `#list` gained bottom padding so the last row does not end underneath it.
- **The Ask composer's send button becomes the stop button, and stop means abort.** One button, both icons in the markup, CSS showing one, and `setSendMode` as the single place the icon, label and job change together — the same rule as `setRefreshBusy` on the sky. The form's submit handler branches on `state.busy`, so Enter cancels exactly as the click does. `AbortController` closes the connection, which cancels the server's request context, and `Asker` already treats a cancelled context as a hard stop rather than something to retry. An abort is **not** a failure: `postJSON` returns `{aborted: true}` rather than "could not reach the server", the turn reads "Stopped." and keeps the sources the free FTS5 search already found. The budget is then **re-read from the server**, not adjusted locally, because the model may have been called before the connection closed and `llm_calls` is the only place that knows.
- **Clearing the chat is a real DELETE, and it refunds nothing.** `DELETE /api/chat/history` → `store.DeleteChatTurns`. Clearing only the DOM would put every question back on the next open, since the page reloads its history each time. It deletes `chat_turns` alone: `chat_calls_today` is counted from `llm_calls` (`LLMCallsByRoleOn`), so the day's spend stands — a clear button that reset the cap would be a way to spend the budget twice. The button hides itself when there is nothing to clear, and re-shows `#intro` afterwards rather than leaving a blank screen with no invitation on it. A test pins that the cost log survives.
- **The sky header's run state is a deliberate copy of the Settings header's, not shared code.** Same four facts, same wording, ~30 lines of `renderRunState` in `app.js` and six CSS rules duplicated into `style.css`. Sharing them would mean `app.js` importing from `settings.js`, or a component's layout moving into `tokens.css` — and the reason the sky loads six assets is that neither of those happened. If they drift, copy the wording again — the copy is currently short on screen with the full phrasing in a `title`, because that line shares a row with the wordmark, the date, the toggle and three buttons, and "Running", "LLM" and "to run" are all said by something already next to them. Two things fall out of it worth keeping: a failing role is **named** (`Ask failing`, not `1 role failing`), which is what lets chat appear here at all — the rule keeping chat off the star map's *banner* exists so a dead Ask screen cannot pass for a broken morning run, and a named role cannot; and `setRefreshBusy` is the single place the refresh button's state is set, because "spinning" and "unclickable" are one state and drifted apart when they were two assignments. It disables **before** the POST, not when the poll returns `running` — there is a second between the click and the first status, and a click inside it reached a 409 that looked like a button ignoring you. The **same copy rule covers Signal quality's window picker**: it is `.view-toggle`'s segmented pill duplicated into `settings.css`, because switching Today / 7 days / 30 days is the same kind of choice as switching Sky / List and the instance should have one control for that job. Its one deviation is `width: max-content` — in the sky's header `.view-toggle` is a flex item and hugs its buttons for free, while on a screen it is a block child and would stretch full width and stop reading as a group. Its aria deliberately does **not** copy: `.view-toggle` has two real panels for `aria-controls`, the picker has none, so it stays `group` + `aria-pressed` rather than claiming a second tablist over a region that already carries `role=tabpanel`. An underline tab strip was tried first and rejected — the page's own tabs sit directly above it, and two strips compete over which one says where you are.
- **Settings is a page with horizontal tabs, not a popover with a sheet** (spec rev 5, decision #20). `settings/index.html` holds the tab strip and one `#screen`; `settings.js` renders into it through `screenFrame`. Tabs are `<a href="#topics">` and the fragment *is* the router — `screenFromHash` on load and on `hashchange` — which is what makes the sky's banner able to open straight on `settings/#model`, and what makes Back step between screens. The gear on the star map is a plain link with no handler; `app.js` imports nothing from here.
- **A provider can be switched off — through the API only; there is deliberately no control on the Model screen.** The switch was built into the provider row and then taken back out by owner decision; the routing half stayed. So the capability is real and enforced, but the only way to reach it is `PATCH /api/providers/{name} {"active":false}`. The **indication** half shipped separately (2026-09-05) and the control did not: a disabled row draws an `off` badge, greys its mark, and the section gains a note naming the PATCH — said only when something is actually disabled, since otherwise it is a line about a control that is not there. Three things about that badge are deliberate. It reads **before** the key badge, because a disabled provider is not routable whatever its key is doing. It is **neutral, not `bad`** — being off is something the owner did on purpose, and it can never be the cause of a broken run, since PATCH 409s on a role's primary. And **only the mark fades**, never the row: the artwork is an `<img>` and carries no contrast requirement, while dimming the url and the env var with it would put the row's text back under the AA floor the palette exists to clear. `llm.Provider.Disabled` is stored as `disabled` so that **absent means on** — the registry is an unmigrated JSON blob in `settings`, and an `enabled` flag would read every existing entry as off on upgrade. The API says `active`, matching topics and sources. `Registry.Lookup` still returns a disabled entry (the screen has to list it to switch it back on); `Registry.Resolve` — the routing path — refuses it with `ErrProviderDisabled`. A disabled hop in a fallback chain is **skipped, not recorded**: nothing was called, so an `llm_calls` row would bill a call that never happened and make a parked vendor look like a failing one. That does not weaken "every attempt gets a row" — a skip is not an attempt.
- **Switching off a provider a role's *primary* runs on is refused, not allowed-and-caught.** `PATCH /api/providers/{name}` 409s and names the roles (`Config.RolesUsing`, primaries only — a fallback-only provider is free to park, which is the ordinary use). An unset API key is something the environment did to you and readiness catches it; this is something the owner just did, and the honest moment to say "that would stop the morning run" is at the click, in the screen where the roles are two sections below. `RoleReadiness` still reports a disabled primary defensively, for a registry edited some other way. Note this guard covers `RoleChat` too — that does **not** fold chat into `Ready()`, which still covers classifier and synthesizer only; it just stops the Ask screen being broken silently.
- **Provider marks are the vendors' own artwork, bundled as files in `web/assets/img/providers/`.** One per registry preset, mapped by `PROVIDER_MARKS` in `settings.js`, shown *instead of* the provider's name on the Model screen — so the name survives only as the `<img alt>` and the tile's `title`, and neither may be dropped. Same rule as the fonts and the Milky Way: fetched once and committed, **never hotlinked**, because §6's offline guarantee covers images. They are `<img>` rather than inlined markup — full-colour artwork has nothing for `currentColor` to do, and inlining would put ~15KB of path data into a parsed script. Each file was re-framed to a square `viewBox` around its own ink so six sources share one optical axis; a `currentColor` fill is meaningless in an `<img>` and was replaced with the vendor's colour. A provider with no file falls back to a monogram, which is also what any provider the owner adds gets — so deleting a file degrades, never breaks. Provenance, the trademark position and Twemoji's CC-BY attribution for `litellm.svg` are in that directory's README; keep it with the files.
- **`chat.css` and `settings.css` each carry a blanket `[hidden] { display: none !important }`.** Same trap as `#sheet` and `.field` before it: an author `display` beats the UA `[hidden]` rule, and both files hide elements by class rather than by id — so the id-based guard in `web/css.test.js` cannot see them. The blanket rule covers whatever gets added to those pages next; a test pins each one.
- **Hacker News is ONE source carrying many keywords, never one source per keyword.** `signals.source_count` is `count(DISTINCT source_id)` over `item_sources` and it decides the gold "hot" flag (§6, ≥ 3), so a row per keyword made one HN story matching three of them present as three independent outlets. Measured on a real instance before migration 007 collapsed it: **25 of 31 gold stars were gold on Hacker News alone**, one Launch HN post counted seven times. The keyword list lives in that row's config as `queries`, each entry keeping its own `min_points` — the threshold is per keyword because Algolia matches literally, so queries are broad single concepts and a broad one needs a higher bar than a niche one (`LLM` at 25 floods the sky, `MCP` at 100 goes silent). `HNConfig.Normalized` folds the old single-query shape in, so a hand-edited row still parses; do not write that shape. The fetcher does per-QUERY try/continue and only errors when every query failed, mirroring §10's per-source rule — and the Sources screen routes a new HN keyword into the existing row rather than creating a second one, because two HN rows reintroduce the bug one keyword at a time.
- **Hacker News keywords run at a LOW points bar; the firehose runs at a HIGH one, and the pairing is the design.** Two separate findings force it. First, **Algolia is typo-tolerant by default and `hnSearch` must send `typoTolerance=false`** — without it `MoE` returned 554 stories over 30 days with *none* containing the term, `xAI` 520 at 2%, `RAG` 275 at 0%, and `GLM` matched *Gmail* while the actual GLM-5.3 release sat buried among 126 junk hits. With it off the same queries return 2–4 stories each, nearly all on-term. It is deliberately NOT paired with `restrictSearchableAttributes=title`: that reaches 100% precision by dropping every story that names the model only in its body, which is exactly what a "Show HN: … using open-weight models" post is. Second, once precision no longer depends on popularity, **the points bar should be low** — the median AI-shaped HN story scores **3**, and 1,435 of 1,549 in a 30-day sample sat under 50 points, so `min_points` was throwing away the model releases the source exists to catch (measured after the change: `Claude Code status lines` at 11 points, `Kimi Work agent sessions` at 20). `firehose_min_points` is the opposite case — a keyword-less pass for the big story no keyword anticipated — and it must stay high, because a firehose at 50 points sees only **7%** of AI-shaped stories while dropping it to 1 means reading 1,008 stories a day of which ~95% are not about AI. Keywords cover "we didn't guess the vocabulary"; the firehose covers "nobody thought of it at all". Neither replaces the other, and **`hnFetch` must follow pages** — one page is 100 hits over a 72-hour window, and `search_by_date` sorts newest first, so a single page silently drops the OLDEST stories, which is what a missed run most needed.
- **Deduplication now has three levels, not two.** Spec §4 names URL canonicalization at ingest and LLM clustering at synthesis; `sources.SameArticle` sits between them and catches the same article at a different URL (a syndicated republish, an AMP variant, changed permalinks). A fuzzy match becomes an **attribution, never a discard** — two outlets carrying one story is exactly what `source_count` measures and what makes a star gold. It is deliberately conservative, and the reason is asymmetric cost: a miss leaves one extra row the synthesizer usually clusters anyway, while a false merge destroys a story before anything judged it, with no trace in the sky. Similarity alone was not enough — token-overlap scored `GPT-5` vs `GPT-5.1` at 0.94 and `is fair use` vs `is not fair use` at 0.95 — so numbers and negations are hard disqualifiers on top of the 0.92 threshold. `TestKnownMissSingleSubstitutedPreposition` pins the trade-off; read it before retuning any of those numbers.
- **`sources.kind` cannot gain a new value without a table rebuild.** Migration 001 pins `CHECK (kind IN ('rss','hn_search','youtube_rss'))`, SQLite cannot widen a CHECK via ALTER TABLE, and the documented rebuild needs `DROP TABLE sources` — which fails while `items.source_id` references it, with no way to disable foreign keys from inside a migration (each runs in a transaction, where the pragma is a no-op). The paste-a-link inbox works around this as an ordinary `rss` row carrying `{"manual":true}` and created **paused**; `Ingest` skips it explicitly. Anything else needing a new kind faces the same wall.
- **Source import is additive and verifies by default.** It never deletes what a file omits, because an export goes stale as soon as either side edits and losing the owner's pruning is not a recoverable trade. New feeds are fetched through the real fetcher first, per the seeding convention above, and anything that fails lands paused-with-a-reason rather than dropped.
- **Sources can be generated from a topic, and every URL is probed before it becomes a row.** `POST /api/topics/{id}/sources/suggest` → `pipeline.SuggestSources`, driven from the Topics screen. It runs on the **synthesizer's** chain under its own `suggest` role: recalling real publications and real feed paths is world knowledge, and a cheaper model does not fail loudly here — it invents more URLs that the probe then throws away. Off the per-run budget (`offRunBudget`) like test and chat, since a button is not a run; the daily cap still applies. The whole feature rests on `sources.ProbeFeed`, which exists rather than reusing `RSSFetcher` because a probe needs two things the `Fetcher` interface deliberately does not carry: **where redirects landed** and **the feed's own title**. Both are load-bearing. The redirect is the `openai.com/blog/rss.xml` → `/news/rss.xml` case: a candidate looks distinct from everything configured right up until it is fetched, so **dedup happens after the probe, never before**, or one masthead gets two rows and is double-counted in every `source_count` it touches. The title is the check on "is this the publication the model claimed" — the same question the scraped-channel-ID trap answers wrongly — and it is also the name fallback when the model gives none. Feeds and keywords are then treated **asymmetrically, on purpose**: a verified feed is written as a **paused** `rss` row carrying `suggested_for` in its config (a note, not a reference — `Identity()` keys on `url` alone, so it cannot affect dedup, and a deleted topic leaves a harmless dangling id, same trick as the inbox's `{"manual":true}`); a keyword is only **proposed**, never written, because there is exactly one Hacker News row (migration 007) and it is live, so appending would put a guess into tomorrow's run unreviewed — and a keyword cannot be paused on its own, since the row is the unit of active. One click is the review. Note this also diverges from import deliberately: import parks a doubtful feed paused-with-a-reason because the *owner* named it and is owed the row, whereas here the *model* named it and everything accepted is already paused, so a failed probe is **rejected outright** rather than written — a row the owner has to delete is worse than a line on screen saying "is not a feed". `min_points` from the model is clamped, because out of range is quiet in both directions: too high silences the keyword and reads as a keyword that simply found no news.
- **`Settings.addHNKeyword` is the only place a Hacker News keyword is written, and the write must carry the rest of the config forward.** `PATCH /api/sources/{id}` **replaces** `config` wholesale, so sending `{queries}` alone drops `firehose_min_points` — silently switching off the keyword-less pass that exists to catch the story no keyword anticipated. Nothing looks broken; the sky just quietly stops finding those. The Sources screen's add field and a suggestion's Add button both route through this one function for that reason, plus the older one (a second HN row undoes migration 007 one keyword at a time). `query` is the single key deliberately dropped, because `hnQueries` has already folded the legacy single-keyword shape into the list and keeping it would watch that keyword twice.
- **Trending normalizes titles in SQL, and the double-space collapse is load-bearing.** `RecurringStories` groups on a normalized title because the synthesizer rewords its titles every run. Turning `:` and `-` into spaces leaves two spaces where there was one, so without the two `replace(…,'  ',' ')` passes the reworded copies do not group and the function silently finds nothing — which is exactly how it failed the first time.
- **Transcripts write into `items.summary`, which is why the stage runs before classify.** The classifier reads title and summary and nothing else, so a summary landing after classification makes every video a run late — indistinguishable from the feature not working. `item_transcripts.summary_base` holds the item's original description so applying a summary is idempotent: rebuilt from the base, never prepended to whatever is already there. Failure rows are written deliberately — without them a video with captions disabled is refetched every run forever — and `none` (permanent) is stored differently from `error` (retryable).
- **The weekly round-up defaults to written, not sent.** `schedule_weekly_day` seeds to `mon`, so a fresh instance has **three** cron entries; delivery is what decision #10 turned down, not composition. An empty day switches composition off — and note `config.str()` cannot express that, because it substitutes the default for an empty value, so `ScheduleWeeklyDay` is read raw from the settings map. Defaults for that key live in bootstrap's seed, not in the read.
- **The weekly round-up is a CHOSEN LIST, not an essay, and the model supplies none of the facts.** It asked for 200-350 words of prose first, and prose over a week is a compression problem the model solves by averaging — 60 stories into 300 words produces "a clear shift into production-grade agent engineering accelerated", which is true of every week in this field and names nothing a person can go and read. The composer now asks for `{"lead": "...", "items":[{"id":12,"note":"..."}]}` and **renders the list itself**: title, source count, topic, date and link all come from `signals`, so the round-up cannot name a story that does not exist or attribute one to outlets that did not carry it. Asking a model to copy twelve URLs back accurately is a bet with no upside — it has the ids. An id not in the week, or repeated, is dropped (same whitelist reasoning as `Asker.sanitizePlan`), and unparseable output **degrades rather than fails**: the fallback lists the top signals by corroboration with the `reason` the synthesizer already wrote for each. A round-up is not worth losing a week over. The body is plain text with hard newlines because it is read in two places and must work in both — `text/plain` email, and a `.weekly-body` element whose CSS is `white-space: pre-wrap`.
- **The round-up collapses signal rows into stories before the model sees them, keyed on `primary_url`.** Without it the same story is offered several times and the model picks it several times, correctly — a real digest opened with "Meta releases Muse Glimmer" at 1 and "Meta launches Muse Glimmer" at 2, and listed one coding agent at 5 and again at 12. Two unrelated causes, both by design: every run composes **its own day's** signals while the sky shows seven days, so a story that stays newsworthy gets a fresh row each morning with a reworded title; and a story matching two topics **is** two signals (§4), the case the canvas draws as one shared star. `collapseWeeklyStories` is the same decision `groupSignals` makes on the canvas, in the same words, because a story is a URL in both places. The first row for a URL wins its title and date — the query is ordered `source_count DESC, score DESC, run_date DESC`, so that is the best-corroborated and most recent reading — counts take the **maximum, never the sum** (three readings of one story are not three more outlets carrying it), and every topic it matched is printed, because a story crossing two topics is the most interesting thing a week contains. Note the fixture trap this exposed: `seedWeek` gave five signals one URL, so after the change it was describing one story five times.
- **Sending a round-up is not composing one.** `POST /api/weekly/send` (`WeeklyRunner.Deliver`) delivers what is stored; `POST /api/weekly/run` composes and optionally delivers. The manual send button could not be run-with-`deliver:true` — that would replace the prose the owner is reading with a different draft, bill a synthesizer call to send something already written, and on a week it decides not to rewrite send nothing at all. `Deliver` also needs no model configuration, which is the point on the day the send is being retried *because* the provider was down. Both channels off returns **200 with `deliver_note`**, not an error: nothing was sent, and that is a configuration state the screen reports.
- **Each delivery channel is a card whose switch sits in its title, and "off" disables its fields rather than hiding them.** Two toggles collected at the bottom of one seven-field form said nothing about which fields either governed, and the webhook URL sat in a grid of SMTP settings it has nothing to do with. `Settings.channelCard` pairs the switch with exactly what it turns on and flips `disabled` **in place** — a rebuild would go through `screenFrame` and `replaceChildren()` away the confirmation the flip just produced. Disabled, not hidden: a hidden field cannot be read, and reading the relay a channel *would* use is exactly what you want when working out why nothing arrived. The accepted trade is that fields cannot be filled in before the channel is switched on; "Send a test" still works either way, so verify-before-committing is switch on → fill in → test.
- **A bad weekly schedule must never take the daily one down.** The daily sky is the product; `Scheduler.Reload` logs and skips a malformed weekly spec rather than returning an error, and a test pins that the two daily entries survive.
- **SMTP credentials follow the provider-key contract exactly**: the settings row holds an env var *name*, `/api/settings` returns the name plus a resolved boolean, and no endpoint ever returns the value. Defaults target Resend's relay (`smtp.resend.com:587`, username the literal `resend`, password `RESEND_API_KEY`). If STARTTLS is advertised and then fails, the send fails — never a plaintext fallback.
- **The SMTP envelope is not the `From:` header, and `digest_from` is written in header form.** `MAIL FROM`/`RCPT TO` carry an RFC 5321 path — a bare addr-spec — while `From:`/`To:` carry RFC 5322 mailboxes, which is the only place a display name is legal. The seed is `Interstellar <onboarding@resend.dev>`, so sending the configured string down the envelope produced `MAIL FROM:<Interstellar <onboarding@resend.dev>>` and a 501 "Bad sender address syntax" from Resend — on **every send from every fresh instance**, correctly refused. `notify.SendEmail` parses both fields with `net/mail` and uses `.Address` for the envelope and `mail.Address.String()` for the headers; that second half also RFC 2047-encodes a display name in Vietnamese (§9), which was going out as raw UTF-8. Recipients come from `mail.ParseAddressList`, never a comma split, because a display name may contain a comma (`"Mai, Tam" <t@x>` is one recipient). `SMTPConfig.Problem()` parses as well, so a malformed address is a sentence on the Weekly screen rather than a numeric code arriving after a connection, a handshake and an authentication. Note this trap walked straight through the test suite once: `fakeRelay` answered `250` to any envelope at all, so it now enforces a bare path and answers 501 otherwise — a fake that is lenient where the real thing is strict tests nothing.
- **A delivery test must separate "broken" from "not set up".** `POST /api/delivery/test` returns `ping_note` instead of `ping_error` when there is no webhook URL and the switch is off: nothing was tested, so nothing failed. It is an error only when `ping_enabled` is on with no URL — the case the round-up itself would trip over, and the one `describeDelivery` already reports on the screen. Reporting an unconfigured channel as a failure put a red line about a feature the owner never asked for next to the email they were actually testing, and turned the whole result red when that email had just sent. Red means act on it, or it stops meaning anything.
- **Fixed column counts where the grouping is the point.** `.grid` auto-fits, which is right for a bag of fields; `.grid.quad` and `.grid.duo` are explicit `repeat(N, minmax(0,1fr))` because a group whose shape changes with the window has stopped being a group — Schedule's two groups are four across, Weekly's delivery fields are two, and they step 4→2→1 and 2→1 at breakpoints rather than reflowing continuously. Both set `align-items: start` and give `.field-label` a two-line `min-height`, so one wrapped label does not drop its input half a line below the rest of its row. Help text in a quarter-width column has to be written short — a sentence becomes eight ragged lines and buries the field it belongs to.
- **A flex item's margin adds to its basis.** `flex-basis: 100%` on an item with `margin-left: 52px` is a row 52px wider than its container, which is how the provider row overflowed at 380px while the page itself reported no horizontal scroll. Use `calc(100% - <margin>)`.
- **A UI action must not re-render the screen it just reported into.** `screenFrame` calls `replaceChildren()`, so `rerenderCurrent()` destroys the confirmation message that triggered it. This has bitten the Model screen and the weekly screen; update the affected element in place instead. Same reason `refreshModel` skips the rebuild when the settings signature is unchanged, and refuses to rebuild at all while a field on the screen has focus.
- **The classify watermark may only pass items EVERY ready topic judged.** It is a single high-water mark, so it advances over an unbroken *prefix* of item ranges: if one topic's batch failed on the first slice, nothing behind it can be claimed either. Advancing regardless left a permanent hole in that topic's coverage, visible only as a topic that mysteriously matched nothing. The cost is that a persistently failing topic stalls the watermark and re-classifies the same items each run — which is the right way round, because it is bounded by the per-run cap and loud (a problem every run, a zero in the hit-rate view), whereas silent loss is neither. **Per-topic stats deliberately do NOT follow that prefix**: gating them the same way made one failing topic blank the hit-rate view for every topic, destroying the diagnostic that would identify it. Re-classifying double-counts numerator and denominator together, so the rate is unchanged.
- **Every setting that changes when the scheduler fires belongs in `scheduleKeys`.** The reload used to be a two-key if/else, so adding the weekly round-up meant changing its day silently required a restart — while the screen that changed it said "the schedule was rebuilt". A test pins the weekly case.
- **Never truncate a string with `s[:n]`. Use `sources.Truncate`.** On Vietnamese text -- which §9 keeps topic definitions in, and which Vietnamese feeds carry -- 27% of byte offsets fall inside a multi-byte rune (measured, not estimated). `json.Marshal` does not error on invalid UTF-8; it substitutes U+FFFD, so the damage arrives as a mojibake character in the database and on screen rather than as a failure anyone would notice. Nine sites had this before it was found, across four hand-rolled copies of the same rune walk; there is now one implementation, and it delegates to `strings.ToValidUTF8`.
- `specs/` is history. Amend it by adding a revision, not by silently rewriting a decision.
- **`.dockerignore` is written narrow, and must stay that way.** The build stage is `COPY . .`, so it was shipping 33MB of context — 19MB of it `bin/`, which the container rebuilds from source anyway. None of it reached the image (the distroless stage takes only the binary and an empty `/data`), but it invalidated the cache every build and left a dev database one stray `COPY` from the final layer. Exclusions are **by name, never by sweep**: `web/assets` is embedded with `//go:embed all:assets`, and `all:` takes dotfiles and READMEs along with everything else, so `web/assets/img/README.md` — the Milky Way's licence, which §6 requires to travel with the image — and the providers directory's attribution note are both one `*.md` rule away from vanishing. The build would still succeed; the licence would simply stop being distributed with the thing it licenses. Verify a change to this file by building and checking every asset is still reachable, not by reading it.
- **Distribution is local `docker build`, decided 2026-08-11.** No image is published and none should be: an instance is one person's container built from this repo. The plan carried "publish to GHCR" as an open item; it is now closed as *won't do*, so don't reopen it as tidying. `make docker-multiarch` still verifies amd64 and arm64 both build.
- **YouTube's public RSS feeds are gone (2026-09-08), and discovery runs on the Data API.** Every `/feeds/videos.xml` id form — `channel_id`, `playlist_id`, `user` — answers **404**, from a response whose own `server:` header reads "YouTube RSS Feeds server"; the same URL with **no parameters returns 400**, so the route is live and still validating query strings while resolving no id for anybody. Channel pages answer 200 throughout, and a known-stable channel 404s identically with a browser User-Agent from a working network — so it is not a block and **not stale channel ids**, which is the wrong diagnosis the convention below invites when nine sources break at once. Do not re-resolve ids. `YouTubeFetcher` now calls `playlistItems.list` on the uploads playlist (the channel id with `UC` swapped for `UU`), which costs **1** quota unit against `search.list`'s 100. Two things keep this cheap to have done: the kind stays **`youtube_rss`**, because migration 001's CHECK cannot be widened and what changed is how the kind is fetched rather than what it means; and the channel id is **read back out of the retired feed URL** when config carries no `channel_id`, so existing rows needed no data migration. The key follows the env-var-name contract (`youtube_api_key_env`, seeded `YOUTUBE_API_KEY`), is resolved per run in `Ingest` into `sources.Options`, and an unset one is reported **by variable name**.
- **Transcripts are a separate breakage, and an `error` row is already terminal.** The signed caption `baseUrl` returns an empty body, so `fetchTrackText` fails with "did not parse as json3"; on a real instance the stage has produced **0 `ok` against 144 attempts**. It does not matter much: YouTube items still matched a topic **56%** of the time on title and description alone — roughly double Hacker News — so discovery carries the value, not captions. And do not "fix" the retrying: `VideosNeedingTranscripts` treats `status <> 'ok'` as **done**, so a failed row is never re-fetched. The status comment's "may be worth another attempt after a code change" describes a manual intent, not automatic behaviour. What looks like retrying is the finite tail of video items that have no row yet, draining at `transcripts_per_run`.
- **Never seed a source URL you have not run through the real fetcher.** `make feedcheck URLS="…"` does it with the app's own parser. A feed can return 200 in a browser and yield zero items; worse, a YouTube channel ID scraped from page HTML will happily serve *someone else's* channel — a `"channelId":"UC…"` regex matches the recommended-channels sidebar, which is how Karpathy's row once got 3Blue1Brown's ID. Resolve channels from `rel="canonical"` and confirm against the title the feed itself returns.
- **The press feeds are one row per outlet, and they are what makes a star gold.** TechCrunch, The Verge, MIT Technology Review and VentureBeat exist in the list for `source_count`, not for being first: the practitioner feeds almost never corroborate each other — one person writes one post — so before them almost all corroboration came from Hacker News. Section feeds, not whole-site ones, which is what keeps them to ~7-20 items a day. One row per masthead, for exactly the reason migration 007 collapsed Hacker News. Two notes for whoever extends this: `openai.com/blog/rss.xml` **307s to** `/news/rss.xml`, so those are one feed and adding both would double-count OpenAI; and **Anthropic publishes no feed of its own** — no `<link rel="alternate">` on either page, 404 at `/rss.xml`, `/news/rss.xml`, `/news/rss`, `/news/feed` and `/feed.xml` (checked 2026-08-18). It is covered by two **unofficial mirrors** of first-party pages, both verified through the real fetcher, and they are two rows because they are two publications: `claude.com/blog` (product and customer writing) and `anthropic.com/news` (corporate and research). The cost to know about is that a cross-post between them counts twice toward `source_count` — not enough to gild on its own, enough that one press pickup would. Being mirrors is the standing risk and it is the acceptable kind: one that stops updating goes quiet rather than wrong, and §10's per-source try/continue means one that disappears cannot take a run down. A mirror *can* rewrite a title or a link, which no first-party feed can — worth knowing before either row is trusted for more than reading. The openrss.org mirror was tried first and rejected: it answers 200 with an HTML page, the "200 in a browser, zero items in the parser" trap this convention exists for.
- **The canvas draws from `sky.shown`, never `sky.stars`.** `shown` is the filtered subset; rendering, hit-testing and constellation lines must all read it or they disagree with each other — a filtered-out star that stays clickable is the failure mode.
- **The header counts STORIES, and the number is smaller than the signal count on purpose.** A signal is one story for **one topic** (§4), so a story matching two topics arrives from `/api/sky` as two rows — two titles, two reasons, written separately by the synthesizer — and `groupSignals` merges them by `primary_url` into the single shared star §6 asks for. Measured on a real instance: **110 rows, 99 stars**, all 11 collapses two-topic stories. The header said "99 signals", which reads as a cap or a lost run and was reported as exactly that. "Stories" is also the only word that survives the view switch, because the list renders a shared story under **both** of its topic groups: rows on screen there are the 110, stars are the 99, stories are 99 in both places. The arithmetic lives in the element's `title`, not the header, which has no room for it. Do not "fix" this by counting rows — the count's job is to match what a person can point at.
- **Star rendering bakes its gradients and draws its core.** `drawStar` builds ~6 gradients per call (0.22ms/star, flat with scale); `spriteFor` bakes layers once and blits them (~0.05ms/star, improving with scale as sprites are shared). Layers split on two axes and both matter: by **motion**, because a sprite can only carry a rigid transform (`pulsing` scales with the hot pulse, `glint` also rotates, `glow` does neither, so a cold star's four soft layers collapse into one `body` sprite); and by **required sharpness**, because blitting at a fractional scale resamples — the hard core is never baked, since softening it visibly breaks §6's "pinprick that makes it read as a star". Only the hovered star takes the full direct path. Measured 2–4.5× faster, growing with star count; this is what stops the sky slowing down as the day fills it.
- **Never merge scattered small shapes into one path.** `drawDust` bucketed 200 particles by alpha and issued one `fill()` per bucket — the same instinct as the star sprites, and it cost two thirds of the frame rate (21fps against 55). The dots in a bucket are spread across the whole sky, so one path per bucket meant ~18 fills a frame whose bounding boxes each spanned the entire canvas, and the rasterizer sets up over the box, not the ink. Batching draw calls is usually right; batching geometry this sparse inverts it. Spec §11 has the numbers.
- **Measuring canvas cost: only end-to-end frame rate is trustworthy.** Timing the draw calls measures JS record time, because rasterization is deferred. Forcing a flush with `getImageData` charges a readback whose cost tracks the dirtied area, not the work — that one made full-screen blits look like 40ms and dust like 0.3ms. Interleave conditions across rounds so machine drift cancels, and compare ratios, not absolutes: the same code measured 55fps and 16fps on this machine hours apart, purely on load.
- **The sky skips frames, so anything that changes the picture must set `dirty`.** With motion off and the view settled every frame is identical, and repainting 4.4M device pixels to reproduce it is the single largest cost in the renderer — the floor no layer toggle can move. `frame()` returns early when `still && !moved && !dirty`. The failure mode is silent and one-directional: a missed `dirty` leaves a stale image with nothing to explain it, while a spurious one only costs a frame. Set it in anything touching layout, filters, layer visibility, hover identity, or the motion gate. `easeView` must also snap at its threshold — the ease is asymptotic, so without it the sky never settles and never skips.
- **Sky layer visibility is view state, not config.** `SKY_LAYERS` lives in the browser via `loadShow`/`saveShow`, never the `settings` table: nothing about it reaches a run, and the settings table's "applies on the next run" contract is wrong for something that applies on the next frame. Labels and stars are deliberately not toggleable — the label is the only place §10's "No signal today" is rendered, and the stars are the product. The motion toggle ORs with `prefers-reduced-motion` so it can turn motion off but never on.
- **The constellation join is a spanning tree, and the `lines` layer defaults off.** `constellationEdges` runs Prim's over a topic's stars in `buildConstellations` — once per rebuild, never per frame, like everything else in there. It replaced a polyline in array order, which is the API's *score* order: on a 45-star topic that drew 44 segments zigzagging across itself, joining stars adjacent in score and far apart on screen. Edges hold references to the caller's star objects, not copies, so they track relayout. **Shared-star ties were removed, twice over — don't add them back.** §6's "place star between constellations" reads like an instruction to draw a line and is not: it is met by *placement*, and membership is stated by the tooltip, the detail panel and both list groups. Drawing all 49 was a tangle; narrowing them to the hovered star worked and was still judged worthless. The per-star `shared` flag survives for one job only — a shared star must not lift a constellation label, or two topics' names drift together until they overprint.
- **`web/assets/img/milky-way.webp` is AI-generated and personal, non-commercial use only.** That turns the "no published image" decision from a preference into a licence condition — see `web/assets/img/README.md`, which ships inside the binary with it. `drawMilkyWay` is the fallback, so removing the file degrades the background rather than breaking the build.
- **The Milky Way is a bundled photograph, composited with `lighter`.** `web/assets/img/milky-way.webp` is baked into `bgLayer` once per layout, so it costs a decode at startup and nothing per frame — and 3ms to bake against the hand-drawn band's 7.2ms. Additive is load-bearing: the image is light on black, so `lighter` adds the band and its grain while the empty sky between the stars contributes nothing; source-over paints that black over the gradient and flattens the depth. The procedural nebula is skipped when the photo is in use for the same reason. `drawMilkyWay` is the fallback, not dead code — it renders before the image decodes and if it never does, which is what stops §6's offline guarantee resting on one asset. `loadBand` must set `dirty`, since the frame loop may be idle when the image lands.
- **UI symbols are inline SVG, not text characters.** The bundled Noto Sans subset does not cover them: `⌂` (U+2302) was rendering in a system fallback font, which is why it needed a hand-written `font-size` and would have been tofu on a machine without one. §6 requires the UI to render offline from bundled fonts. A button holding an SVG also needs explicit flex centring — a `<button>` centres a text character on its own, but an inline `<svg>` sits on the text baseline.
- Filter thresholds derive from the encoding functions (`starRadius`, `starAlpha`), not from raw scores. The classifier returns 1–5 and the match threshold clips it at 4, so a plausible-looking `score >= 6` matches nothing at all.

## Phase discipline

Spec §"Roadmap beyond Phase 0" defines later phases as **gates, not dates** — each opens only when a specific failure mode shows up in real use. The rule has been honoured mostly in the breach: Phase 1's list and two Phase 3 items (Ask, search) were all built ahead of their gates by owner decision, which is why the Status section above reads as it does. That makes the rule *more* load-bearing now, not less, because the untested part is no longer "is it built" but "is it any good" — and the answer needs real use, which is the thing a gate was measuring in the first place. So: before building anything further out, say which failure mode in actual daily use is asking for it. The Phase 0 non-goals list in §2 is short and deliberate.
